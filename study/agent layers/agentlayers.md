# Agent Architecture: Layer-by-Layer Analysis

> 정보가 들어오는 순간부터 최종 출력까지 — AI 에이전트를 구성하는 레이어의 전체 구조

---

## Overview

에이전트는 단일 모델이 아니라 여러 레이어가 쌓인 시스템이다. 각 레이어는 정보를 변환하거나, 필터링하거나, 보강하거나, 라우팅한다. 아래는 정보 흐름 순서대로 정리한 7개 레이어다.

```
[Raw Input]
    ↓
1. Ingestion Layer     — 입력 수집 및 파싱
    ↓
2. Context Layer      — 컨텍스트 조립
    ↓
3. Memory Layer       — 기억 조회 및 주입
    ↓
4. Security Layer     — 안전성 검사 및 권한 제어
    ↓
5. Reasoning Layer    — 추론 및 계획
    ↓
6. Action/Data Layer  — 툴 실행 및 데이터 접근
    ↓
7. Output Layer       — 응답 생성 및 후처리
    ↓
[Final Response]
```

---

## Layer 1 — Ingestion Layer (입력 수집)

**역할:** 외부에서 들어오는 모든 신호를 에이전트가 처리할 수 있는 형식으로 변환한다.

### 입력 유형
| 유형              | 예시                       |
| --------------- | ------------------------ |
| Text            | 사용자 메시지, 문서              |
| Structured data | JSON, CSV, DB 쿼리 결과      |
| Multimodal      | 이미지, 오디오, 비디오            |
| Events          | webhook, API 콜백, 스케줄 트리거 |
| Tool results    | 이전 액션의 반환값               |

### 주요 처리
- **토큰화(Tokenization):** 텍스트를 모델이 읽을 수 있는 토큰 시퀀스로 변환
- **청킹(Chunking):** 긴 문서를 컨텍스트 윈도우 크기에 맞게 분할
- **멀티모달 인코딩:** 이미지 → 임베딩 벡터, 오디오 → 텍스트 트랜스크립트
- **입력 정규화:** 포맷 통일, 인코딩 처리, 노이즈 제거

### 핵심 제약
컨텍스트 윈도우(context window)는 이 레이어에서 가장 큰 병목이다. GPT-4o는 128K 토큰, Claude Sonnet 4.6은 200K 토큰을 지원하지만, 실제 유효 처리량은 더 낮다.

## Layer 2 — Context Layer (컨텍스트 조립)

**역할:** 모델에 전달될 "프롬프트 패키지"를 조립한다. 에이전트의 정체성, 규칙, 현재 대화가 모두 이 레이어에서 통합된다.

### 컨텍스트의 구성 요소

```
┌─────────────────────────────────────────────┐
│ SYSTEM PROMPT                               │
│  - 에이전트 역할 정의 (persona)              │
│  - 행동 규칙 (instructions)                 │
│  - 출력 포맷 가이드                          │
├─────────────────────────────────────────────┤
│ INJECTED CONTEXT                            │
│  - 검색된 문서 (RAG 결과)                   │
│  - 메모리에서 불러온 정보                    │
│  - 툴 실행 결과                             │
├─────────────────────────────────────────────┤
│ CONVERSATION HISTORY                        │
│  - 이전 메시지 (human/assistant 턴)         │
│  - 압축된 요약 (long conversation)          │
├─────────────────────────────────────────────┤
│ CURRENT USER INPUT                          │
└─────────────────────────────────────────────┘
```

### 컨텍스트 관리 전략
- **컨텍스트 압축(Context Compression):** 오래된 대화를 요약해서 토큰 절약
- **동적 주입(Dynamic Injection):** 질문 관련성에 따라 문서를 실시간으로 삽입
- **우선순위 지정:** 중요 정보를 프롬프트 앞쪽에 배치 (attention sink 효과 활용)
- **컨텍스트 캐싱(Context Caching):** 반복적으로 쓰이는 시스템 프롬프트를 캐시해 비용 절감 (Anthropic의 prompt caching)

### 이 레이어가 중요한 이유
동일한 모델이라도 컨텍스트 조립 방식에 따라 성능이 크게 달라진다. 프롬프트 엔지니어링의 대부분이 이 레이어에 해당한다.

## Layer 3 — Memory Layer (기억 시스템)

**역할:** 에이전트가 단일 컨텍스트 윈도우를 넘어서 정보를 저장하고 불러올 수 있게 한다.

### 기억의 4가지 유형

#### 3-1. Working Memory (작업 기억)
- 현재 컨텍스트 윈도우 안에 있는 정보
- 가장 빠르지만 가장 일시적 — 대화가 끝나면 소멸
- 용량 제한: 컨텍스트 윈도우 크기에 종속

#### 3-2. Episodic Memory (에피소드 기억)
- 과거 대화, 특정 이벤트, 상호작용 기록
- 저장소: 파일, DB, 벡터 DB
- 예: "지난주에 사용자가 A 프로젝트를 물어봤다"
- 구현: 대화 로그 → 임베딩 → 벡터 검색

#### 3-3. Semantic Memory (의미 기억)
- 사실 지식, 도메인 정보, 정적 지식 베이스
- 저장소: 문서 DB, 벡터 DB, 지식 그래프
- 예: 회사 제품 스펙, 법률 조항, 투자 기준
- 구현: RAG (Retrieval-Augmented Generation)

#### 3-4. Procedural Memory (절차 기억)
- 작업 수행 방법 — 에이전트의 행동 패턴
- 모델 파라미터 자체에 내재화되거나 툴 정의로 외재화
- 예: "IM 작성 시 항상 이 구조를 따른다"
- 구현: 파인튜닝, 시스템 프롬프트, 툴 스키마

### 메모리 검색 메커니즘
```
Query → Embedding → Vector Search → Top-K Retrieval → Context 주입
```
- **유사도 검색:** cosine similarity, dot product
- **하이브리드 검색:** 벡터 검색 + 키워드 검색 결합
- **재순위화(Reranking):** 검색 결과를 관련성 순으로 재정렬

## Layer 4 — Security Layer (보안 및 안전)

**역할:** 입력과 출력 양방향에서 위험 요소를 차단하고, 에이전트의 권한을 제어한다.

### 4-1. Input Guardrails (입력 필터)
- **프롬프트 인젝션 감지:** 악의적 지시가 시스템 프롬프트를 덮어쓰려는 시도 차단
- **PII 감지:** 개인정보(이름, 주민번호, 신용카드) 자동 마스킹
- **유해 콘텐츠 분류:** 폭력, 불법, 규정 위반 요청 필터링
- **입력 유효성 검사:** 예상치 못한 형식의 입력 거부

### 4-2. Permission & Authorization (권한 제어)
```
에이전트가 할 수 있는 것 (Allowed)
  - 파일 읽기 / 쓰기 (지정 디렉터리만)
  - API 호출 (화이트리스트된 서비스만)
  - DB 쿼리 (읽기 전용 vs 읽기/쓰기)

에이전트가 할 수 없는 것 (Restricted)
  - 시스템 명령 실행 (--no-verify 등)
  - 외부 네트워크 무제한 접근
  - 자기 자신의 시스템 프롬프트 수정
```

- **최소 권한 원칙(Least Privilege):** 작업에 필요한 최소한의 권한만 부여
- **Human-in-the-loop:** 고위험 액션은 사람 승인 필요 (e.g. 결제, 삭제)
- **액션 로깅:** 모든 툴 실행을 감사 로그에 기록

### 4-3. Output Guardrails (출력 필터)
- **민감 정보 누출 방지:** API 키, 비밀번호, 내부 시스템 정보 차단
- **편향 감지:** 특정 집단에 대한 편향된 표현 필터
- **환각(Hallucination) 감지:** 사실 주장에 대한 신뢰도 스코어링
- **포맷 유효성 검사:** 요구된 JSON 스키마, 출력 길이 준수 여부 확인

### 4-4. Adversarial Robustness
- **탈옥 시도(Jailbreak) 방어:** 역할극, 가상 시나리오를 통한 규칙 우회 시도 차단
- **멀티-에이전트 신뢰 경계:** 외부 에이전트의 지시를 사용자 지시와 동일하게 신뢰하지 않음
- **인젝션 분리:** 데이터 영역(문서 내용)과 지시 영역(시스템 프롬프트)을 구분

## Layer 5 — Reasoning Layer (추론 및 계획)

**역할:** 주어진 정보를 바탕으로 목표를 이해하고, 단계를 계획하며, 의사결정을 내린다. 에이전트의 "두뇌" 에 해당하는 레이어다.

### 추론 패러다임

#### 5-1. Chain-of-Thought (CoT)
- 중간 추론 단계를 명시적으로 생성
- "먼저 A를 확인하고, B와 비교한 뒤, C를 결정한다"
- 복잡한 수학, 논리 문제에서 정확도 향상
- 단점: 토큰 비용 증가

#### 5-2. ReAct (Reason + Act)
```
Thought → Action → Observation → Thought → Action → ...
```
- 추론(Thought)과 행동(Action)을 번갈아 수행
- 툴 사용 에이전트의 기본 패턴
- 관찰(Observation) 결과를 다음 추론에 반영

#### 5-3. Tree of Thought (ToT)
- 여러 추론 경로를 병렬로 탐색
- 각 경로를 평가하고 유망한 경로 선택
- 복잡한 계획 수립, 창의적 문제에 적합
- 비용이 가장 높음

#### 5-4. Extended Thinking (내부 추론)
- Claude Sonnet 4 / 3.7 등이 지원하는 방식
- 모델이 응답 전에 내부적으로 긴 추론 과정을 실행
- 사용자에게 보이지 않는 "생각의 스크래치패드"

### 계획(Planning) 구조
```
Goal Decomposition
  └── Subgoal 1
        └── Task 1-1 → Tool Call
        └── Task 1-2 → Tool Call
  └── Subgoal 2
        └── Task 2-1 → Tool Call
```
- **선형 계획:** 순차적 스텝 실행
- **병렬 계획:** 독립적인 태스크를 동시에 실행 (multi-agent)
- **적응형 계획:** 중간 결과에 따라 계획을 실시간으로 수정

## Layer 6 — Action / Data Layer (행동 및 데이터 접근)

**역할:** 에이전트가 실제 세계와 인터페이스하는 레이어. 모델의 언어 능력이 실제 결과로 연결되는 지점이다.

### 6-1. Tool Use (툴 사용)
에이전트가 호출할 수 있는 툴의 유형:

| 카테고리    | 예시                           |
| ------- | ---------------------------- |
| 파일 시스템  | Read, Write, Edit, 파일 검색     |
| 코드 실행   | Python REPL, bash 명령, 테스트 실행 |
| 웹       | 검색, 웹 크롤링, API 호출            |
| 데이터베이스  | SQL 쿼리, 벡터 DB 검색             |
| 커뮤니케이션  | 이메일 발송, Slack 메시지, 알림        |
| 다른 에이전트 | 서브에이전트 실행, 에이전트 오케스트레이션      |

#### 툴 호출 사이클
```
1. 모델이 툴 사용 필요성 판단
2. 툴 이름 + 파라미터를 구조화된 형식으로 출력
3. 런타임이 실제 툴 실행
4. 결과를 컨텍스트에 주입
5. 모델이 결과를 바탕으로 다음 단계 결정
```

### 6-2. Data Retrieval (데이터 검색)
- **RAG (Retrieval-Augmented Generation):** 질문 관련 문서를 벡터 DB에서 검색해 컨텍스트에 주입
- **GraphRAG:** 지식 그래프를 활용해 엔티티 간 관계를 포함한 컨텍스트 제공
- **하이브리드 검색:** BM25(키워드) + 벡터 검색 결합

### 6-3. Multi-Agent Orchestration (멀티에이전트)
```
Orchestrator Agent
  ├── Subagent A (조사 담당)
  ├── Subagent B (코드 작성 담당)
  └── Subagent C (검증 담당)
```
- **Orchestrator:** 전체 계획 수립, 서브에이전트에 태스크 분배
- **Specialist Agent:** 특정 도메인/작업에 최적화된 에이전트
- **통신 방식:** 공유 메모리, 메시지 패싱, 파일 기반 핸드오프
- **장점:** 병렬 처리, 전문화, 긴 작업의 분할 정복

## Layer 7 — Output Layer (출력 생성)

**역할:** 모델의 내부 상태를 사용자 또는 다운스트림 시스템이 소비할 수 있는 형태로 변환한다.

### 7-1. Response Generation (응답 생성)
- **텍스트 생성:** 자연어 응답, 요약, 설명
- **구조화된 출력:** JSON, XML, 마크다운 — 스키마 강제 적용 가능
- **코드 생성:** 실행 가능한 코드 블록
- **스트리밍:** 토큰 단위로 점진적 출력 (UX 개선)

### 7-2. Output Formatting (출력 포맷팅)
- 지정된 스키마(JSON Schema)에 맞는 구조화 출력 강제
- 길이 제한 적용
- 특정 언어/톤 준수 (예: 한국어 보통 말투)
- 마크다운 렌더링 vs 플레인 텍스트 선택

### 7-3. Post-Processing (후처리)
- **팩트 체킹:** 외부 소스와 대조해 주장의 신뢰도 검증
- **포맷 변환:** 텍스트 → PDF, 텍스트 → PPTX 등
- **번역/현지화:** 다국어 출력
- **품질 평가(Self-Critique):** 모델이 자신의 출력을 평가하고 개선

### 7-4. Feedback Loop (피드백 루프)
```
Output → Evaluation → [Good? → Deliver] / [Bad? → Revise → Reasoning Layer]
```
- 출력 품질이 기준 미달이면 추론 레이어로 되돌아가 재생성
- Human feedback → RLHF/RLAIF를 통해 모델 자체 개선
- 런타임 평가: 자동화된 평가 에이전트(judge model) 활용

## Full Stack Summary

| 레이어 | 핵심 질문 | 주요 기술 |
|--------|-----------|-----------|
| 1. Ingestion | "무엇이 들어왔나?" | 토큰화, 청킹, 멀티모달 인코딩 |
| 2. Context | "무엇을 모델에게 보여줄까?" | 프롬프트 엔지니어링, 컨텍스트 캐싱 |
| 3. Memory | "이전에 알고 있던 것은?" | RAG, 벡터 DB, 에피소드 저장 |
| 4. Security | "해도 되는 일인가?" | 가드레일, 권한 제어, 인젝션 방어 |
| 5. Reasoning | "어떻게 해결할까?" | CoT, ReAct, ToT, 계획 수립 |
| 6. Action/Data | "실제로 무엇을 했나?" | 툴 호출, DB 접근, 멀티에이전트 |
| 7. Output | "어떻게 전달할까?" | 구조화 출력, 후처리, 피드백 루프 |

## 실전 적용: 에이전트 설계 시 레이어별 체크포인트

**인프라 비용이 가장 큰 레이어:** Memory (벡터 DB 운영), Reasoning (토큰 사용량)

**실패가 가장 자주 발생하는 레이어:** Context (잘못된 정보 주입), Security (프롬프트 인젝션)

**성능 개선 ROI가 가장 높은 레이어:** Context + Memory — 모델을 바꾸기 전에 이 두 레이어를 먼저 최적화하라

**사람 개입(Human-in-the-loop)이 필요한 레이어:** Security (고위험 액션 승인), Output (최종 품질 검토)
